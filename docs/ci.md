# CI

Two separate things, easily conflated:

1. the workflow a **generated project** ships with
2. the workflow **this repo** runs to prove the generator works

## Generated project CI

`files/.github/workflows/ci.yml` in every template. It builds the image and runs the two
tasks — the same two commands the developer runs locally, which is the point:

```yaml
name: ci

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read

jobs:
  test:
    runs-on: ubuntu-latest
    env:
      dockerhub_username: ${{ secrets.DOCKERHUB_USERNAME }}
    steps:
      - uses: actions/checkout@v7.0.1
      - if: env.dockerhub_username != ''
        uses: docker/login-action@v4.8.0
        with:
          username: ${{ secrets.DOCKERHUB_USERNAME }}
          password: ${{ secrets.DOCKERHUB_TOKEN }}
      - run: docker compose build
      - run: make lint
      - run: make test
```

Deliberately minimal. It is a starting point the project owner will edit, not a
framework. No matrix, no release job.

**`files/.github/workflows/actions.lock` ships beside it**, pinning both of those actions
to a commit, because a tag can be repointed and `uses: actions/checkout@v7` would then run
whatever it was repointed at. The file is generated by `gh actions-lock` and is identical
in all forty-seven templates — the lockfile keys a workflow by path, and every template's
workflow is the same file. `lint` asserts that every `uses:` in the shipped workflow has
an entry in the shipped lockfile, and
[actions-lock.yml](../.github/workflows/actions-lock.yml) regenerates it nightly, because
a lockfile naming a commit that upstream has since made unreachable fails a run outright
— worse than the floating tag it replaced.

**It builds rather than pulls, on purpose.** The published image would be faster, but a
generated project's CI exists to test that project's own `Dockerfile`; pulling would
test the upstream image instead and quietly ignore every edit the owner had made to it.

That is also why the `docker/login-action` step survives: building resolves the base
image from Docker Hub, which rate-limits — see [rate limits](#rate-limits). It is
guarded on the secret rather than required, so a project that never hits the limit needs
no setup at all and one that does has somewhere to put credentials. The secrets context
is not available to an `if`, which is why the value goes through `env` first.

## This repo's CI

The real proof. A template is only correct if a cold machine can bootstrap it and get a
green test, so that is exactly what CI does, for every template — and then publishes the
image it just tested.

One workflow:

```
lint     ─┐
contract ─┼─> image-amd64 (one leg per changed template, cap 8) ─┬─> manifest ─> cleanup
remote   ─┤   image-arm64 (one leg per changed template, cap 8) ─┘   merge :main  prune
scope    ─┘   build, lint, test, push

contract and remote run on ubuntu, macos and windows; the windows leg of
each drives bootstrap.ps1 rather than bootstrap.sh
```

Each `image` leg is one template on one architecture:

```yaml
      - run: >-
          ./bootstrap.sh ${{ matrix.template }} ../scaffold --no-pull
          ${{ (github.event_name == 'schedule' || github.event_name == 'workflow_dispatch') && '--no-cache' || '' }}
      - name: lint the scaffold
        working-directory: ../scaffold
        run: make lint
      - name: the suite left the tree clean       # git status --porcelain
      - name: fmt changes nothing                 # make fmt, then status again
      - name: the remaining targets run           # make build, make help
      - name: every placeholder was substituted   # grep for a leftover token
      - name: a second test run reuses the first  # down -v, cold, warm, compare
      - name: the kitchen sink is deletable       # rm the sink, make test
      - name: push what the tests passed
        if: ${{ needs.scope.outputs.publish == 'true' }}
        run: |
          image=$(sed -n 's/^ *image: *//p' ../scaffold/compose.yaml)
          docker tag "$image" "${image}-amd64"
          docker tag "$image" "${image%:*}:${GITHUB_SHA}-amd64"
          docker push "${image}-amd64"                     # both retried; see
          docker push "${image%:*}:${GITHUB_SHA}-amd64"    # the first-push race
```

**The six checks between the lint and the push were all documented promises that
nothing verified.** The contract's definition of done has eleven items and CI enforced
two of them; `make fmt` had never run anywhere, no test had ever deleted a kitchen sink,
and `git status` was only ever asserted before a build, where the lock files it is meant
to catch cannot have appeared yet. Each sits ahead of the push deliberately: a template
that fails one withholds its own publish and leaves `:main` where it was.

**The second tag is how `manifest` knows what this run pushed.** It runs per template and
cannot see a matrix sibling's result, and a `:main-amd64` written minutes ago is
indistinguishable from one left behind weeks ago — so a template whose both legs failed
had the previous digests re-merged and published green. A tag naming the commit cannot be
mistaken that way, because no earlier run wrote this sha, so `manifest` merges from those
and skips any template missing one. It used to be an uploaded artefact per leg, which did
the same job through a channel that had nothing to do with images.

That is the whole idea: **the bootstrap builds it, the bootstrap tests it, and the thing
that passed is the thing that ships.** `--no-pull` because the point is the `Dockerfile`;
pulling the published image would test the previous commit's toolchain against this
commit's templates, and a broken `Dockerfile` would go green.

Layers are a different question from images. Every template's `compose.yaml` names its
published image under `cache_from` as well as under `image`, so a `--no-pull` build still
reuses what the last one produced — buildkit matches a layer only when the instruction and
its inputs are identical, so an edited `Dockerfile` rebuilds from the edit down and a
broken one still goes red. See
[containers.md](containers.md#published-images-are-a-cache-not-the-pin).

It used to be two workflows that did not know about each other. `ci` built twenty-six
images, tested them and threw them away; `publish` built fifty-one more and pushed those,
untested. Seventy-seven builds to ship fifty-one images, and the fifty-one that shipped
were not the ones that passed. Merging them removes a whole matrix of builds from every push.

`fail-fast: false` matters: when an upstream image bumps and breaks three languages, you
want all three in one run.

The image name is read out of the scaffold's `compose.yaml` rather than rebuilt from the
template id — the same reason `bootstrap.sh` reads it back instead of composing it, so the
tag pushed here cannot drift from the one `compose` will pull.

### What gates what

- **`scope` chooses which templates to build, not whether to build.** A template's image
  can only change when that template changes, so `scope` diffs the pushed range and selects
  the `templates/<id>/` directories in it. A push that adds one template builds one
  template; docs, the README and `bootstrap.ps1` build nothing at all.

  Two paths are the exception, because they feed every image: `bootstrap.sh`, which
  scaffolds each project before it is built, and this workflow, which does the building. A
  change to either selects everything.

  It answers "everything" whenever the question cannot be asked — a new branch, a force
  push, the weekly run. A template that appears in the diff but no longer has a
  `template.env` is dropped, so deleting one builds nothing.

  **This replaced building everything on every push**, which had been doing two jobs: it
  gated by path, and it caught drift — a base image tag that moved under us, an apt package
  that stopped existing. [The weekly run](#the-weekly-rebuild) took over the second job,
  which is what makes selecting by path safe. Before that, landing one template rebuilt
  sixty-six legs to prove that thirty-two of them had not changed.

  This started as a `paths` filter on the old publish workflow's trigger. Merged, it has to
  be a job: a trigger filter would skip the script's own tests too.
- **`scope` gates publishing too**, on the same selection plus two more conditions: the
  event is not a pull request, and the ref is `main`. A PR builds and tests; it never
  pushes.
- **Everything cheap gates everything expensive.** `lint`, `contract` and `remote` are
  ungated and run first; the image jobs `needs` all three plus `scope`, with an `if` that
  checks only `scope`'s selection. Wrapping that `if` in `!cancelled()` — which it used to
  be — overrides the success requirement `needs` already carries, so a broken script or a
  shellcheck nit spent seventy-four builds proving itself. Three minutes against
  seventy-four builds is not a trade worth thinking about.
- **`manifest` and `cleanup` are ordered, not gated.** Both `needs` what comes before them
  and both keep `!cancelled()`, because a matrix reports one aggregate result: a strict
  gate on `image-amd64` would let one template's failed leg withhold publishing for the
  other thirty-six. Per-template granularity comes from the tags instead — see
  [publishing images](#publishing-images).

`packages: write` is granted to the three jobs that push, never at workflow level, so the
`lint`, `contract` and `remote` jobs keep read-only tokens.

### The commit path

A runner has no `user.name` or `user.email`, and `bootstrap.sh` treats that as
non-fatal — it initialises the repository, skips the commit, says so, and still exits
`0`. Left alone, CI would prove the fallback and never the normal path, so every job that
runs the bootstrap configures an identity first.

The `contract` job then asserts what the commit contains: one commit, on `main`, with a
clean tree afterwards. It also asserts that `.env` exists and is **not** tracked. That
file is generated rather than templated — it carries the host's uid and gid so the
container writes files you own — and committing one machine's ids into a project is the
kind of bug that survives review.

The bootstrap's own build and test steps are what assert the generated project works.
CI does not re-run them — a non-zero exit from `bootstrap.sh` with code `4` or `5`
already says which half failed.

### Two architectures, in parallel

Containers are Linux whatever the host is, so running the matrix on three operating
systems would test Docker Desktop, not the templates. No Windows or macOS leg builds
an image; they test the script instead, which is a different job.

There are two *architectures*, on native runners rather than under QEMU: emulating a
toolchain build costs more than the whole matrix, and public repositories get
`ubuntu-24.04-arm` free. That is about the runners, not about the templates --
`arm32` runs QEMU *inside* its image on both of them, because its tests are firmware
for a chip neither runner is.

Two matrices, one per architecture, both gated on `scope` and
`lint` and neither waiting on the other. They ran in series for exactly one revision; the
barrier made every arm64 leg wait for the slowest amd64 one and bought nothing beyond
"amd64 ships first".

**What two caps of eight add up to.** `max-parallel` is per job, so the peak is 16
concurrent builds rather than 8. The pull count per run does not change — one or two per
leg either way — and Docker Hub's limit is counted per account over six hours rather than
per instant, which is why the `concurrency` group that stopped successive pushes stacking
whole matrices is the thing that actually fixed the `429`. 16 is also a long way below the
51 in flight when one appeared. If one shows up again, the dial is `max-parallel: 4` in
both jobs. Most runs now select one or two templates and come nowhere near either
cap; the weekly one is what fills them.

Each leg pushes its own `:main-<arch>` tag and a per-template `manifest` job merges them
into the `:main` index `compose.yaml` names. The merge takes whichever architectures it
finds rather than naming both, because a template that gains or loses one should not need
an edit here and because a template whose tests failed has no new tag to merge. The edge
that follows: if a template's amd64 leg fails and its arm64 leg passes, `:main` indexes a
fresh arm64 beside the previous commit's amd64. That was already true of a failed *build*
and is now also true of a failed test; the run is red either way.

**The first push of a new template is a race, and the push step retries because of it.**
ghcr creates the package when a template is published for the first time, and both
architectures try to create the same one at once. The loser is denied — after every layer
has already uploaded, so the log looks like a permissions problem rather than a collision.
`ada` landed that way: its amd64 leg was denied, its arm64 leg was not, and `manifest` did
exactly what it is told to and published an arm64-only `:main`. Three attempts ten seconds
apart cost nothing when nothing is wrong, and re-running the failed leg by hand confirmed
the cause: the identical push succeeded once the package existed.

Both architectures build and test on a pull request; neither pushes. arm64 was the
architecture nothing had ever run, so it is worth the runner time to find out before the
merge rather than after.

The template list is **generated**, not written out: the `scope` job globs
`templates/*/template.env` into a JSON array and all three matrices consume it via
`fromJSON`. That is the same glob `bootstrap.sh` discovers templates with, so adding a
language needs no CI edit — which is what the contract's "no registry to update" promise
requires.

### The weekly rebuild

```yaml
  schedule:
    - cron: '17 4 * * 1'
  workflow_dispatch:
```

Selecting templates by path means nothing builds a template unless it changes, and
"build everything on every push" had been accidentally serving as drift detection — a
moved base-image tag, an apt repository that stopped carrying a version, a Hackage
outage. Monday morning replaces the accident with something deliberate, off the hour
because scheduled runs on the hour are the ones GitHub delays.

**It is now the only run that builds everything**, which makes it load-bearing rather
than belt-and-braces: a template nobody has touched since it landed is proven on Monday
or not at all. If it ever stops running, the first symptom will be a template that has
been broken for a while.

**It is also the run that builds from nothing**: the schedule and a manual dispatch are
the only two that pass `--no-cache`. Every other run reuses published layers, which is
fast and cannot tell you whether a `Dockerfile` still builds without them.

`workflow_dispatch` is there because a run that matters this much should not be
testable only by waiting for Monday. It selects every template for the same
reason the schedule does: it has nothing to diff against.

**It publishes.** That is a decision rather than an oversight, and it has a consequence
worth stating: `:main` can move with no commit behind it. This is consistent with the
images being [a cache, not the pin](containers.md#published-images-are-a-cache-not-the-pin) —
the `Dockerfile` is still the authority on every version — but a reader who assumes
`:main` corresponds to a commit is wrong, and would be wrong in a confusing way if nobody
had written it down.

Scheduled runs share the `ci-${{ github.ref }}` concurrency group with pushes to `main`,
deliberately: a push should cancel an in-flight weekly rather than run sixteen builds
beside it.

### Layer caching

There is none, and that is a choice rather than an omission.

The build happens inside `bootstrap.sh`, which runs `docker compose build` in the target
directory and offers no hook for extra flags. `docker compose build` has no
`--cache-from`/`--cache-to` either; those are compose-file keys, and every template's
`compose.yaml` uses the scalar short form `build: .`, which has no room for sub-keys. So
caching would mean one of:

1. **`cache_from`/`cache_to` in every template's `compose.yaml`.** Twenty-six edits, and
   it puts CI-specific configuration into the generated project, which the user then has
   to understand or delete.
2. **A documented build-flag passthrough in `bootstrap.sh`** — one variable it reads and
   appends — set from CI. One edit to the script, none to the templates, and the generated
   project stays clean.

Route 2 is the way in if it is wanted, and it is not obviously worth taking. The old
publish workflow did cache — `type=gha`, `mode=max`, scoped per template and
architecture — against an Actions cache that is 10 GB for the whole repository. `haskell`
alone is 6.4 GB, so the large legs evicted each other and the legs that hit were the fast
ones anyway.

The sting has also mostly been drawn: `haskell` was the one leg that made this urgent, and
installing its linters from apt took it from never finishing to 99s. The slowest leg is now
`ocaml` at about four and a half minutes.

### Script quality

One job, `lint`, and a gate on everything after it:

- `shellcheck bootstrap.sh`
- `actionlint` over this repo's workflows and every template's `files/.github/workflows/`
- `hadolint` over every template's `Dockerfile`
- `gh actions-lock --verify`, which is the whole of this repo's action pinning

`bootstrap.ps1` is checked where PowerShell is, which is the Windows leg of `contract`:

- `PSScriptAnalyzer`, with the repo's own settings file
- the same five exit codes the other two legs assert of `bootstrap.sh`
- a diff of both scripts' `--dry-run` file list, for every template
- a diff of both scripts' `--list` output, byte for byte, and the shape `cli.md`
  specifies: one tab-separated id and display name per template, sorted by id

`lint` also sweeps the templates themselves, which nothing did before: the required files,
the four that must stay byte-identical to `templates/c/files/`, the `.dockerignore`
exclusions, the six Makefile targets, the ban on POSIX tools in a recipe, a `help` that
reaches its text without a shell, and a shipped lockfile that pins every `uses:` in the
shipped workflow. Every one of those was a contract rule held up by review alone, which is
how two `.dockerignore` files lost their source exclusions without a leg going red.

Those two diffs are the only things that have ever compared the two entry points. They are
kept in step by hand, and a drift between them would otherwise be invisible. Each side
generates its list in its own shell: `bash` invoked from PowerShell is whatever is first
on `PATH`, which on a machine with WSL is not Git Bash.

### The remote path

The matrix above exercises clone mode. Remote mode — the documented one-liner — has its
own failure surface and needs its own job: the ref-pinning logic, the archive download,
the extract, and the temp-directory cleanup.

```yaml
  remote:
    strategy:
      matrix:
        os: [ubuntu-latest, macos-latest, windows-latest]
    runs-on: ${{ matrix.os }}
    env:
      sha: ${{ github.sha }}
    steps:
      - run: |
          BOOTSTRAP_REF=$sha /bin/bash -c \
            "$(curl -fsSL "https://raw.githubusercontent.com/acodeninja/bootstrap/$sha/bootstrap.sh")" \
            -- javascript ../out --no-git --no-build
          test -f ../out/package.json
```

Pinning both URLs to `github.sha` tests the commit under review rather than whatever is
on `main`, and proves the two refs stay in step — the bug where a script served from one
ref fetches templates from another.

A second step asserts the failure path, which is the half with something to clean up: a
`BOOTSTRAP_REF` naming no branch must exit `6`, write nothing to the target, and leave no
temporary directory behind. `mktemp -d` does not write to `/tmp` on macOS, so the
check asks `$TMPDIR` where it did.

The Windows leg runs the PowerShell one-liner instead, which
[install.md](install.md#windows) documents and nothing used to test. Two details of that
form are now load-bearing in CI as well as in the docs. The happy path invokes the script
block in process, because `iex` cannot pass arguments to the code it runs. The failure
path cannot: a script block built from a string runs in the *caller's* process, where the
script's `exit` would end the step rather than report to it, so the exit code has to come
from a child — and `BOOTSTRAP_REF` is handed to that child through the environment,
because `powershell -Command` strips the quotes from an assignment inside the command
string and the bad ref would be run as a command, leaving the variable unset and the
script fetching `main` perfectly happily.

So `bootstrap.sh` is covered in both modes on Linux and macOS, and `bootstrap.ps1` in
both modes on Windows — each script where its users run it.

### Failure-mode assertions

Negative tests asserting the exit codes in [cli.md](cli.md) rather than just "it failed":

| Command                                                            | Expect               |
| ------------------------------------------------------------------ | -------------------- |
| `bootstrap.sh`                                                     | `1`                  |
| `bootstrap.sh --nosuchflag javascript ../out`                      | `1`                  |
| `bootstrap.sh nosuchlang ../out`                                   | `2`                  |
| `bootstrap.sh javascript .` (non-empty)                            | `3`                  |
| `bootstrap.sh javascript ../out --dry-run` then `test ! -e ../out` | `0`, nothing written |
| `BOOTSTRAP_REF=refs/heads/no-such-branch` remote run               | `6`                  |

Codes `4` and `5` are not asserted — faking an absent Docker daemon or a failing
generated test costs more than it proves.

`javascript` throughout, not `zig`: one template is enough to assert a script's
exit code, and the one with the fastest image is the one to use. The same five run
against `bootstrap.ps1` on the Windows leg.

## Publishing images

Not a workflow of its own any more — the last three steps of each `image` leg, and the
`manifest` job after them. What gets published and when is covered in
[what gates what](#what-gates-what) above; what follows is the shape of the artefact.

Four tags per template, and only one of them is for anyone else to use: `:main` is the
index `compose.yaml` pulls, `:main-amd64` and `:main-arm64` are the platform manifests it
indexes, and `:<sha>-<arch>` is what `manifest` merged from. The sha tags are plumbing
rather than a release — nothing pins to them, and `cleanup` collects them once
`:main-<arch>` has moved on. Pinning a published image is still not a thing you can do;
see [containers.md](containers.md#published-images-are-a-cache-not-the-pin).

Three things keep the pipeline inside Docker Hub's limit, which is counted **per account**
and shared by every leg in flight. All three were added after a run answered `429`:

- `scope`, because a docs-only commit cannot change an image and was rebuilding all
  fifty-one
- a `concurrency` group, because successive pushes stacked whole matrices
- `max-parallel: 8`, because every build resolves its `FROM` and fifty-one at once was past
  the limit however well authenticated

That cap is per job and there are two matrices, so the peak is sixteen rather than eight —
see [two architectures, in parallel](#two-architectures-in-parallel).

Nothing here is urgent, so spreading it out costs nothing that matters.

The build context is a **scaffold**, not `templates/<id>/files`, because the build happens
where the bootstrap put the project. The raw template directory is not buildable anyway:
the manifests the priming layers read still carry `{{TOKEN}}` placeholders — `elixir`'s
`mix.exs` declares `app: :{{PROJECT_SNAKE}}`, which is not valid Elixir — and `haskell`'s
cabal file is *named* with one. Five of the twenty-six failed this way on the first run.
It also means the published image is exactly what a developer's own first build produces,
which is now literally true: it is the same build, by the same script, in the same place.

The images are still a cache rather than a release — see
[containers.md](containers.md#published-images-are-a-cache-not-the-pin). Publishing is
gated on tests because the gate is cheap and per-template, not because a published image
is a promise.

### Pruning what the publish superseded

Every publish leaves digests behind. The new index takes `:main`, the new platform
manifests take `:main-amd64` and `:main-arm64`, and the three they replaced keep existing
with those tags moved off them. Nothing removed them until the `cleanup` job, so they had
been piling up since the first push.

**The rule is "delete every version with no durable tag", and it is safe here for a
reason that does not generalise.** The usual advice is the opposite: an image index's
platform manifests are normally untagged, so pruning untagged digests pulls the platforms
out from under a live multi-architecture tag and every pull breaks. In this registry they
are not untagged — `:main-amd64` and `:main-arm64` exist because that is how the
architectures are published — and `BUILDX_NO_DEFAULT_ATTESTATIONS` means nothing else is
untagged either.

*Durable* is the one word that does the work. A platform manifest also carries the
`:<sha>-<arch>` tag `manifest` merged it from, which outlives `:main-<arch>` by a run, so
"no tag" would have kept every superseded manifest forever. A version is kept when some
tag on it is not a run token — `main`, `main-amd64`, `main-arm64` — and a version whose
only tags are run tokens has been superseded as surely as one with none.

Anything younger than an hour is kept regardless. That is not about the argument above;
it is about a run this one overlapped, whose index is minutes old. Each template is also
capped at twenty-five deletions a run, which is what makes the step finite: the first
real run met a backlog of a thousand and ran out of its timeout part-way through.

`cleanup` runs after `manifest` and never before it. Before the merge, the previous index
is still what `:main` points at, and deleting it then would break the tag it was about to
replace.

## Keeping the pins current

Every version here is pinned: seventy-four `FROM` lines, twelve `ARG *_VERSION` pins inside
`RUN` steps, three of those beside a hand-computed `ARG *_SHA256`, and the actions in
`.github/workflows/`. For a long time nothing moved any of them, which is the other half of
pinning — an unmaintained pin is not reproducible, it is just old, and the first symptom is
a tag upstream has since deleted.

Four kinds of pin, three mechanisms:

| Pin                              | What moves it                                                                            |
| -------------------------------- | ---------------------------------------------------------------------------------------- |
| `uses:` in this repo's workflows | Dependabot, weekly and grouped; it regenerates the matching `actions.lock` entry in the same pull request |
| `FROM` in every template         | Dependabot, weekly, grouped into one pull request across all forty-seven                |
| the shipped `actions.lock`       | [actions-lock.yml](../.github/workflows/actions-lock.yml), nightly, `gh actions-lock --relock` |
| `ARG *_VERSION`                  | nobody — [pins.yml](../.github/workflows/pins.yml) reports them and a human edits the Dockerfile |

**Dependabot cannot see a version inside a `RUN` step**, which is the whole reason
`pins.yml` exists. It reads each `ARG *_VERSION` out of the Dockerfile and asks upstream
what the current release is. For the seven that live on GitHub the owner and repo come out
of the download URL the pin interpolates into, so there is no manifest to drift from what
it describes — and `lci`, which publishes no release at all, is read from its tags instead.
`fantomas` comes from `api.nuget.org`, the three opam packages from the `packages/` tree of
`ocaml/opam-repository`, and `zig` from `ziglang.org/download/index.json`. The job exits
non-zero when anything is behind, so a stale pin is a red scheduled run rather than a
notification nobody reads. It also checks `ACTIONS_LOCK`, the one version pinned in a `run`
step rather than a `uses:` line, and that every workflow agrees on it.

**A grouped Dependabot pull request touches every template**, which makes `scope` select
all forty-seven. The full matrix is then what reviews it, which is the point of grouping
rather than a cost of it.

**The nightly relock does not bump versions.** `--relock` advances a ref that has moved; it
does not take `v7.0.1` to `v8`. It is there because a lockfile is only as good as its last
resolution, and the forty-seven shipped copies have no Dependabot of their own.

## What is not covered

Stated plainly, because the gaps are real:

- **No Windows or macOS leg builds an image.** Neither runner can run a Linux container,
  so the toolchains are proven on Linux only. What those runners do cover is the script:
  `contract` and `remote` run on all three, because every assertion in both is
  `--dry-run` or `--no-build`.
- **The Windows `make` path is still untested.** No Windows runner invokes `make` at all,
  so nothing proves a target works through `cmd.exe`. Two halves of the constraint behind
  it are machine-checked instead: `lint` greps every Makefile recipe for `grep`, `awk`,
  `sed`, `column` and `id`, and asserts that `help` reaches its text through `$(info)`
  rather than the `@echo` whose quotes `cmd.exe` printed literally. A target that reaches
  for a POSIX toolbox fails here rather than on somebody's laptop.
- **`make shell` is never run.** It opens an interactive shell, so a runner with no
  terminal would hold the leg until its timeout rather than failing. Its presence is
  asserted; its behaviour is not.
- **No test asserts the interactive prompt.** Both scripts ask for a missing template
  only when stdin is a terminal, and a runner has none, so `contract` can assert the
  usage error and nothing else. The prompt is hand-tested.

## Rate limits

Docker Hub limits anonymous pulls, and GitHub Actions runners share IP addresses, so
unauthenticated CI hits the limit routinely and reports it as an unrelated-looking build
failure. This repository's `image` jobs authenticate first with `docker/login-action`
when the secrets are there, and build anyway when they are not — a fork's pull
request gets none, and used to fail all seventy legs at that step. A generated
project's CI has always had the same guard.

Each leg logs in to both registries, for opposite reasons: Docker Hub because every
`FROM` comes from there and a weekly run off shared runner IPs is well past the
anonymous limit, ghcr with `GITHUB_TOKEN` because that is where the image goes.

The `lint` job is the exception: it pulls `hadolint` and `actionlint` from Docker
Hub anonymously. Two pulls against a six-hour allowance is not worth a login, and
an image-free job has no scaffold to push.

Dependabot is the other one, and it is not a free pass: resolving a `FROM` across
forty-seven templates is forty-seven manifest lookups a week, anonymously, from GitHub's
own shared addresses. Authenticating it means a `registries:` block in `dependabot.yml`
and the two Docker Hub secrets copied into the **Dependabot** secret store, which is a
different store from the Actions one the `image` jobs read. Until that is done, a weekly
`docker` update job that fails to resolve a tag is the symptom to expect.
